1. Go SSH 별명 CLI 기획

2026-08-24 · Plan 모드

사용자
Go로 CLI 툴을 만들려 한다. SSH 접속 환경을 저장하고 별명을 붙여, 별명만 고르면 키·유저·IP 등을 자동으로 넣어 원하는 SSH에 접속하게 하고 싶다.
에이전트
저장 방식과 선택 UI를 물었다.
사용자
  • 저장: 기존 ~/.ssh/config와 호환 (호스트를 ssh config Host로 매핑)
  • UI: 둘 다 — 인자가 없으면 TUI, 있으면 바로 접속
에이전트
별도 DB/YAML 없이 OpenSSH config의 Host를 별명으로 쓰고, Go에서 SSH 프로토콜을 구현하지 않고 syscall.Exec로 시스템 ssh를 실행하는 계획을 잡았다. cobra, bubbletea, Host 블록 보존 파서를 쓰기로 했다.

5. 테스트와 GitHub Actions 배포

2026-08-24

사용자
테스트 로직을 추가해 달라. GitHub Actions로 자동 배포할 건데, 배포 전에 테스트를 통과해야만 한다.
에이전트
  • sshcfg, connect, tui, CLI 테스트를 추가했다.
  • CLI 테스트를 위해 newRoot()로 커맨드 트리를 분리했다.
  • .github/workflows/ci.yml: PR·푸시 시 go test / vet / build.
  • v* 태그 푸시 시에만, 테스트 잡이 성공한 뒤 바이너리를 GitHub Release에 올린다.

6. 테스트를 test 폴더에 모을 수 있는가

2026-08-24 · Ask 모드

사용자
테스트 파일들을 test 폴더에 모아두면 안 되나?
에이전트
가능은 하지만 Go에서는 권장하지 않는다. go test는 같은 디렉터리의 *_test.go만 그 패키지로 컴파일한다. 한곳에 모으면 비공개 함수(empty, TUI model 등)를 직접 테스트하기 어렵다. 픽스처는 testdata/, 코드는 패키지 옆이 맞다.

7. main.go는 가볍게

2026-08-24 · Ask 모드

사용자
main.go는 최대한 가볍게 가져가는 게 좋다고 들었다.
에이전트
func main은 이미 얇고, 파싱·SSH·TUI는 internal/에 있었다. 남은 무게는 cobra 조립과 학습용 장문 주석이다. 같은 패키지에서 파일만 나누거나, internal/cli로 빼는 단계를 제안했다.
사용자
분리하는 게 유지보수하기 좋겠지?
에이전트
커맨드가 늘수록 이득이다. 다만 지금 규모에서는 파일 분할만으로도 충분할 수 있다. 전역 플래그 변수와 낡은 주석이 유지보수에 더 큰 영향을 준다. 커맨드가 늘 것 같으면 internal/cli가 맞다고 정리했다.

8. CLI를 internal/cli로 분리

2026-08-24 · Agent 모드

사용자
커맨드가 늘어날 수도 있으니 분리해 달라.
에이전트
  • main.go는 cli.NewRoot().Execute()만 호출한다.
  • 서브커맨드는 list.go, add.go, edit.go 등으로 나눴다.
  • 플래그는 패키지 전역 대신 options 구조체로 넣었다.
  • CLI 테스트는 internal/cli/cli_test.go로 옮겼다.

9. 파일별 테스트

2026-08-24

사용자
각각의 Go 파일에 테스트 코드를 작성할 수 있으면 작성해 달라.
에이전트
CLI를 list_test.go 등 소스와 짝이 되는 파일로 나눴다. connect.Exec(ssh 없음), debuglog, TUI 키 입력, sshcfg 헬퍼 테스트를 보탰다. main.go는 진입점만 있어 테스트하지 않았다. --print-cmd를 persistent 플래그로 바꿔 sssh connect --print-cmd도 동작하게 했다.
